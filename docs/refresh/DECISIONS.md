## Scoring version 2: count questions

### How Agree works today

- **Partial credit.** On a 1–5 scale, one point apart scores 75%, two apart 50%. On a ranking, the closer the orders, the more credit.

- **Weighting.** Deeper questions count up to four times as much as light ones. If either of you rates a question important, the higher rating sets its weight.

- **One exception.** PAR-004, “Where does your discipline style fall?”, always scores as full agreement, even firm against gentle.

- So the percentage is a weighted average, and there’s no honest way to write it as “you agreed on x of y”. That’s the line you asked for in recommendation 2.

### What I recommend

- **Count each question as agreed or not.** Agree % is simply the questions you agreed on, out of those you both answered. The line under it always matches.

- **What counts as agreed:** the same choice; the same or a neighbouring point on a 1–5 scale; the same or nearly the same order on a ranking.

- **Importance stops changing the number.** It still marks what matters more to one of you, and it moves those questions up “Talk about next”. Important differences get talked about rather than quietly tilting a percentage.

- **Drop the PAR-004 exception.** Firm against gentle discipline is exactly the kind of difference the app exists to surface.

- **Known stays as it is.** It already counts exact guesses, so “7 of 10 guesses right” matches today.

## Make “private until you’ve both finished” true on the server

### The problem

- The database rules let each partner read the whole session. That includes the other person’s answers in parts that haven’t opened yet.

- The app hides them until you’ve both finished, but only on screen. Anyone who opens the browser’s developer tools, or writes a few lines of code against Firebase, can read their partner’s answers early.

- For questions about faith, sex and the past, that breaks the promise the app makes, and it’s the kind of thing UK data law expects you to protect properly.

- It’s also why Together’s headline can shift before a reveal opens: it counts answers it shouldn’t be able to see yet.

### The fix I recommend

- **Answers go to a private space first.** Each person’s answers, guesses and importance ratings are saved somewhere only they can read.

- **The server publishes a part when you’ve both finished it.** When the second “done” lands, a Cloud Function copies both sets of answers for that part into the shared session. You already have a function that fires at that exact moment (the reveal email), so this builds on it.

- **Partner status still works.** “Judah hasn’t started this part yet” only needs started and finished flags, which stay shared. Answers never are.

- **The rest of the app barely changes.** After publishing, the shared session looks exactly as it does today, so the reveal, scoring and Together read the same data.

### Who can read what

Today

**Shared session**Sarah’s answers · Judah’s answers · done flags

Sarah reads all of itJudah reads all of it

Judah can read Sarah’s Part 2 answers before he has answered, by going around the app.

Proposed

**Sarah’s private space**Only Sarah can read

**Judah’s private space**Only Judah can read

Both finish a part → the server copies that part across

**Shared session**Published parts only · started and done flags

Nobody can read an answer before the part opens for both of you, whatever tools they use.

### What else it covers

- The onboarding starter questions, the Path’s at-the-table answers and written answers use the same route.

- Answers are already write-once in the rules, so there’s no editing-after-sharing problem to solve.

- Existing test sessions get a one-off move: anything in a part that hasn’t opened yet goes back into the private spaces.

- Tested in the Firebase emulator with two accounts and an outsider before it ships, as CLAUDE.md requires.

### Where I differ from the review

- The review folds this into a bigger “Ready to share” system with per-question opt-outs (recommendation 6). This fix doesn’t need that. It keeps your current rule: a part opens when you’ve both finished it.

- The about page and invitation lines from recommendation 1 (“Your answers stay private until you’ve both finished a part”) become literally true with this, so they ship together.

Decided

Option A. Answers, guesses and importance ratings are saved privately and published by a Cloud Function when both of you finish a part. Started and done flags stay shared so partner status keeps working. It ships before new testers are invited, together with the privacy wording from recommendation 1.

Effort: 3 to 5 days including emulator tests and moving existing data.

## “Ready to share”, with per-question hiding

### What the review says

- Finishing a part shouldn’t automatically mean sharing it. Add a separate review step where you tick which answers to share, then press “Ready to share”.

- Only questions you both chose to share would appear in the reveal. Anything one of you held back would vanish, with no trace.

- Either of you could withdraw before the reveal, and changing an answer afterwards would need both of you to approve a new version.

### Why I’d leave it out

- **It works against what TwoAgree is for.** The app exists to get honest answers onto the table before a couple commits. If either of you can quietly drop the hard questions, the reveal shows only the comfortable ones, and the scores look better than the truth.

- **It cuts across your “together” direction.** A private review-and-withhold step makes the reveal a negotiation instead of a shared moment.

- **The real worry is already covered.** The review’s core concern is that answers could leak early. Recommendation 5 fixes that on the server.

- **Holding back already has a route.** 48 sensitive questions offer “Not yet”. Today a “Not yet” quietly drops the question from the reveal and the scores, so it already works a bit like hiding. I’d make it visible instead: the reveal shows “Sarah isn’t ready to answer this yet”. That keeps it honest without forcing an answer. That change belongs with question screens (recommendation 12).

### The one thing worth taking

- Say it plainly at the moment it happens. On the last question of a part, one line above the button: “Your answers open to Judah once you’ve both finished this part.”

- Finishing stays the moment you agree to share. No extra screen, no checkboxes.

## Sign-in and account fixes

### What’s wrong today

- **A real bug:** on a phone nobody has signed in on before, “Already have an account? Sign in” opens the Create account form. A returning user on a new phone hits it first.

- The sign-in screen says “Welcome back” twice, under two different headings.

- Errors are small red lines, and the way to fix them (reset password, sign in instead) is somewhere else or missing.

- The reset confirmation sits inside the sign-in form, so it looks like you still need to sign in.

- Sign-up gives one error for both fields (“Enter your email and a password”) and there’s no way to see the password you typed.

### The fixes

- “Sign in” always opens sign-in. “Create one” always opens create.

- One heading per screen, a show-password eye, and “Forgot password?” right under the password field.

- Errors become a panel with an icon that contains the next step.
